# 業務ロジック・サブセット計画

`docs/mvp-plan.md` で通した縦の一本を、普通の Web アプリの業務ロジックが書けるところまで横に広げるための計画。

## ゴール

副作用を TypeScript 側のインターフェースに逃したうえで残る、純粋なデータ構造とロジックだけの層を
Restricted Lean で書き、npm パッケージとして出せること。クリーンアーキテクチャがすでに引いている線を
そのまま処理系の境界にする。

到達の判定は「注文・課金・権限のような題材を、AST を組み立てるのではなく人が読める構文で書き切れる」
こと。

## 非目標

| 外すもの | 理由 |
| --- | --- |
| Promise / async | 副作用は境界の外。純粋なコアは同期の値変換で閉じる |
| 可変状態・ループ・文 | 評価順序がどこでも観測可能になる。業務ロジックに必要ない |
| Float（IEEE 754） | 金額は最小単位の整数で持つのが業務ロジックの定石で、Int53 / BigInt がそれを担う。入れると NaN・`-0`・丸めが意味論に入る割に得るものがない |
| IO / class / `this` / prototype | 境界の外 |
| 任意の JS を読み込む frontend | 生成する側だけモデル化すればよい。TCB は「消費する JS の機能数」ではなく `JsSem` と `runtime` が抱える構文の数に比例する |

## Approach

広げる方向は 2 つ、それを縛る制約が 1 つ。

- **軸 A — データを記述する力**: 型パラメータ、ネストしたパターン、辞書、文字列操作
- **軸 B — ロジックを組む力**: Array の高階コンビネータ

**制約: 関数は値にしない。** ラムダはコンビネータの構文の一部として書き、独立した値にはならない。
変数に束縛することも、引数として渡し回すことも、返すこともできない。これが計画全体を支えている。

- `Value` にクロージャが増えない。`encodeValue` は全域のままで、`Agree` の `agrees` も値比較のまま
- `.d.ts` に関数型が要らない。境界は JS 互換の値のまま
- ベクタ生成器が変わらない
- `Correct.lean` の `lookup_encodeEnv`（Lean の環境と JS の環境を `encodeValue` で対応させる）が
  そのまま通る。クロージャを値にしていれば、符号化できないものが環境に入るので、対応を関係へ
  書き換える必要があった

これはクリーンアーキテクチャの線引きそのものでもある。ポートは TS 側にあり、純粋なコアはデータを受けて
データを返す。`filter(items, x => x.active)` のように、その場で述語を書ければ業務ロジックには足りる。

## Step 1. 公開関数入口の実行時引数検査 — 完了

**書けるようになること**: 何も増えない。代わりに、外から来た値が宣言した型を破ったとき、生成した JS が
`eval` と同じ `typeError` を投げる。

**触る場所**: `Compile`（`Func` の先頭に検査を挿す）、`Js.runtime`（型ごとの述語）、`Vectors`（型を破った
引数を生成する）。`eval` はすでに入口で `typeError` を返すので `Agree` は変わらない。

**保証の境界**: **既存の証明の仮定が、実際に成立するようになる。** 「`eval` と生成した JS の一致は、宣言
した型を満たす引数について」という但し書きが消える。この計画で保証の境界を実際に押し広げるのは、この
1 歩だけ。

**動かすドキュメント**: `README` の「保証の組み立て」、`docs/mvp-plan.md` の「前提: 宣言した型を満たす
引数」、ベクタ件数。

他のどれとも独立で、小さく、そして業務アプリでは外から来るデータが型を破るのが常態なので最初に置く。

## Step 2. Array の高階コンビネータ — 完了

**書けるようになること**: `map` / `filter` / `reduce`。述語や射影をその場のラムダで書ける。今あるのは
添字読みと長さと自前の再帰だけ。`find` / `all` / `any` は同じ形なので後から足せる。

**`sortBy` は入れない。** 比較関数が全順序であることと、等しいキーに対する安定性が Lean 側のソートと
一致することの両方が要る。ラムダが順序を返す形も他の 3 つと揃わない。独立した課題として切り出す。

**形**: コンビネータは 1 つの構文であって、ラムダを取る関数ではない。`Core.Expr` に
`map (arr : Expr) (binder : String) (body : Expr)` のような形で入れる。`reduce` は 2 つ束縛する。

**触る場所**: `Core`、`Eval`、`Compile`、`JsSem`（走査を Lean 側で回す専用ノード）、`Step`、
`Js.runtime`、`Example.lean`。

**本当のコストは `Step.lean`。** 抽象機械はコンビネータごとに継続フレームが要る（「n 要素の i 番目を
このラムダで写している最中、ここまでの結果はこれ」）。クロージャではなく反復が難しいところなので、
関数を値にしない設計にしてもこの分は消えない。評価順序を間違えれば `stepDisagreementsIn` が捕まえる。

**ネイティブの `xs.map(f)` を直接は呼ばず、`runtime` のヘルパを通す。** ネイティブはコールバックを
`(x, i, arr)` の 3 引数で呼ぶので、アリティを固定するラッパが要る。`runtime` に入るものは検証されて
いない JS でそのまま TCB に乗るので、コンビネータ 1 つが何行足すかを数える。

**ベクタは自動では増えない。** ベクタは公開関数ごとに作られるので、コンビネータは `Example.lean` の
宣言がそれを使って初めて検査される。`map` / `filter` / `reduce` を使う宣言を足すこと。公開関数が
増えるので manifest の `exports` も動く。

**保証の境界**: 変わらない。`Agree` は無傷。

**動かすドキュメント**: `README` のサブセット表と生成物の説明、ベクタ件数、`exports` 件数。

## Step 3. 自前再帰の扱いを決める — 完了

Step 2 が終われば、業務ロジックが自分で再帰を書く必要はほぼ無くなる。ここで態度を決める。今は非停止な
定義を `eval` の fuel が食い止めているだけで、コンパイラは通してしまう。**黙って放置しない。**

- 案 A: 構造的再帰の検査を入れ、通ったものだけ許す
- 案 B: ユーザの再帰を落とし、走査はコンビネータだけにする

**案 B を採る。** サブセットの性格（JS との対応が明快な領域に絞る）に合っており、検査器を TCB に足さずに
穴が閉じる。案 A は、コンビネータで書けない走査が実際に出てきてからでよい。

**形**: 検査を足すのではなく、各宣言を自分より前の宣言だけからなるプログラムに対してコンパイルする。
自己再帰と相互再帰が同じ 1 行で落ち、`compileExpr` の形は変わらない。

**保証の境界**: 穴が 1 つ閉じる。`README` のサブセット表から「構造的再帰」が外れ、「再帰」が外すほうへ移る。

## Step 4. ネストしたパターンとワイルドカード — 完了

**書けるようになること**: `match` が組・入れ子・リテラルで分岐できる。業務ロジックの分岐は「状態 ×
権限」のような組が普通で、今は 1 段・全コンストラクタ網羅・束縛のみ。

**触る場所**: `Core`（パターンを構造として持つ）、`Eval`、`Compile`、`Step`、`Render`。

**網羅性検査は落とさない。** 今の「コンストラクタを漏れなく覆う」検査は、`match` が値を返さない可能性を
消しており、生成コードの分岐連鎖の末尾が到達不能である根拠になっている。ワイルドカードを入れても、
網羅性が検査され続けることを保つ。

**保証の境界**: 変わらない。

## Step 5. 型パラメータ — 完了

**書けるようになること**: `Paginated<T>` / `Validated<E, A>` のような自前のジェネリック型。

**形**: `Ty.named` が型引数のリストを取り、`TypeDef` が型パラメータ名を持ち、`Ty.var` が本体の中でその
パラメータを指す。型の名前からフィールドの**型**を引く場所（`match` のシグネチャ、入口の検査の記述子、
`Value.hasTy`、ベクタ生成）は、すべて型引数を代入してから読む。フィールドの名前を引くだけの場所は
代入が要らない。

**コンストラクタ項は型引数を持つ。** `Validated.valid(x)` からは `E` が決まらない。`none` / `ok` /
`error` が注釈を持つのと同じ理由で、`Expr.ctor` が型引数を取る。

**ベクタ生成の形は変わらなかった。** 具体化を集める必要はない。ベクタは公開関数の引数の型から作られ、
その型はもとから具体的なので、代入は各引数の型を展開する場所で済む。

**再帰型の拒否は宣言側へ移った。** 型引数が入ると、名前で見る occurs check は
`Paginated (Paginated Int53)` まで落としてしまう。宣言のフィールドが自分の名前へ辿り着けるかを
`validateType` で見て、展開する側（記述子・ベクタ生成）は occurs check を持たない。

**保証の境界**: 変わらない。

## Step 6. 文字列操作と辞書 — 完了

**書けるようになること**: `substring` / `split` / `trim` / `startsWith` / `includes` / 大文字小文字変換、
そしてキー付き集合。

**文字列はコードポイントで数える。** `length` は `Array` と同じ `Expr.length` が受け、`String` なら
コードポイント数を返す。ネイティブのメソッドを呼ぶのは `startsWith` と `includes` だけ ——
UTF-16 は前方一致を保ち、引数に孤立サロゲートは入らないので、単位で見た答えとコードポイントで見た答えが
一致する。残りは `runtime` の手書きに落ちる。`trim` は JS のほうが NBSP・BOM・行区切りまで取り、
`toUpperCase` は `ß` を `SS` にして長さを変え、`split("")` は UTF-16 単位に割る。`substring` の添字は
コードポイントで、範囲外は配列の添字と同じく trap する（JS の既定である切り詰めは、黙って短い文字列を
返すので採らない）。

**辞書は `Map`。** 文字列キーの素のオブジェクトは `__proto__` や `constructor` をキーとして受けてしまう。
`get` は `Option` を返すので trap は無く、`set` は新しい `Map` を返す。反復順は `keys` から観測できるので、
既存キーへの `set` が位置を保ち新しいキーが末尾に付くことを `eval` 側でも同じに定義してある。境界に出るのは
`Map` そのもの（`.d.ts` では `ReadonlyMap<string, V>`）で、JSON との変換は用意していない。

**TCB の増分**: `runtime` の非空行が 117 → 172。文字列で +38、辞書で +17。

**保証の境界**: 変わらない。

## Step 7. 構文層

**書けるようになること**: 人が業務ロジックを書ける。`v "a" +' v "b"` は AST の組み立てであって、業務
ロジックの記述ではない。

**これは仕上げではなく必須。** ゴールが「実装できること」である以上、書き味は表現力と同じ資格で目標に
入る。

**触る場所**: 新規の macro 層（Core AST を生む）、`Example.lean` の書き直し。

最後に置くのは、Step 2 / 4 / 5 がいずれも構文を動かすから。先に作ると 3 回書き直すことになる。

## 順序と依存

- Step 1 / 2 / 3 / 4 / 5 は完了
- Step 6 も完了
- Step 7 は最後

## 証明との関係

表現力を足すほど、証明が覆う割合は下がる。`fragment_correct` が覆っているのは `Core.Expr` の 28 形の
うち 3 形（リテラル・変数・条件式）で、残りは `Agree` の全件検査が受けている。Step を 1 つ進めるたびに
分母が増える。

証明側で次に要るのは `docs/mvp-plan.md` の通り type soundness で、これが無いと算術の場合分けが閉じない。
表現力の仕事とは競合するので、どちらを先に進めるかは別の判断になる。ただし**どちらを選んでも、
`README` の「保証の組み立て」と `docs/mvp-plan.md` の到達点は同じコミットで動かす。**
