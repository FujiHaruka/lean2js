# README 全面書き直し — 利用者目線の英語 README

## いまの README が誰に向いているか

いまの README は、この処理系を**作っている側**が読む順で並んでいる。設計方針 → 対象サブセット →
ロードマップ → 保証の組み立て（定理リンク 13 本）→ 生成物 → リポジトリ構成 → 開発ゲート、と来て、
「自分のロジックをどう書き、どう npm パッケージにするか」は 176 行目の小見出しにある。

利用者が最初に知りたいのは順に「何が出てくるのか」「自分のロジックは書けるのか」「どう始めるのか」で、
リポジトリ構成表とゲート一覧は一度も要らない。

## 決定（ユーザー, 2026-09-16）

- **README は英語。** `CLAUDE.md` の言語ルールから `README.md` を外す（`docs/` と
  `templates/**/*.md` は日本語のまま）
- **「保証の組み立て」は README では要約にとどめ、全文は `docs/guarantees.md` に移す**
- **開発者向けの情報（リポジトリ構成表・pnpm ゲート一覧・ロードマップ表）は削除。** 移設先も作らない

- **サンプルコードは現実的な業務ロジックに差し替える。** 1 行の `orderTotal` ではなく、プランの
  ティア・含まれるシート数・超過分の課金・プラットフォーム手数料・割引・入力の検証までを持つ
  サブスクリプション課金の例にする（ユーザー指示 2026-09-16）

## Approach

README を「証明付きの npm パッケージを自分で出したい人」の一本道に組み替える。上から読むと

```
何をする処理系か → 出てくるパッケージ（利用者の利用者が触るもの）→ 3 ファイルで始める
  → 書ける構文 → 定理の書き方 → 何が保証され、何が保証されないか
```

になり、途中でリポジトリの内部に降りない。

内容の判断は 2 つだけ。**成果物として利用者が実際に出会うもの（`.d.ts` の形、ゼロ除算と溢れの trap、
書き出し前に落ちる条件）は残す。処理系の内部事情（モジュール分割、証明の構成、ビルドの回し方）は
落とすか `docs/` へ送る。**

保証の章は**移すだけで、主張は一字も動かさない**。ここは成果物そのもので、要約の段階で表現が緩むと
`CLAUDE.md` の「保証を弱めて緑にしない」に触れる。README に残すのは「証明が届く範囲・書き出し前の
検査・保証の外」の 3 行と、定理へのリンクを持つ `docs/guarantees.md` への導線。

  プランは当時の記録で、最終状態のドキュメントではない

数字（公開関数 67 本、`Core.Expr` 35 形、ベクタ 24466 件、この例題の燃料 482 / 上限 10000、
定理 25 本）は現行の値をそのまま運ぶ。README から移すだけで、測り直す変更は含まない。

## 検査

コードは動かないので Lean と Node のゲートは対象外。確かめるのはリンクだけ:

- README から `templates/verified-package/SYNTAX.md` / `docs/guarantees.md` / Lean リファレンスへの
  リンクが解決すること
- `docs/index.md` と `docs/mvp-plan.md` の付け替えたリンクが解決すること
- `#保証の組み立て` を指すリンクがリポジトリに残っていないこと（完了済みプランの散文中の言及を除く）

## スコープ外だが、この直後にやるべきこと

README を英語にすると、そこから利用者が飛ぶ先 —— `templates/verified-package/README.md` と
`SYNTAX.md` —— が日本語のまま残る。**利用者が構文を調べるために必ず開くのはこの 2 ファイルで、
README よりも利用者向けの度合いは高い。** 英語の README から日本語の構文リファレンスに着地するのは、
今回の書き直しが解こうとしている問題がそのまま残るということ。別コミットで英訳を提案する。
