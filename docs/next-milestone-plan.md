# 次のマイルストーン計画

`docs/business-logic-plan.md` が業務ロジックを書ける幅まで広げたあと、**保証の厚みと配布**へ主軸を移す
ための計画。

## 文脈

到達している地点は、出荷している成果物の数字で言える。公開関数 67 本、型 5 つ、出荷前に照合する
差分ベクタ 24431 件。証明が覆っているのは `Core.Expr` の 35 形のうち 6 形（リテラル・変数・条件式・
`let` 束縛・単項演算・二項演算、二項演算は 16 演算子すべて）で、
残りは `Agree` の全件検査が受けている。manifest に載っている定理は 4 本。

配布の形は決まった（決定 2026-09-07, ユーザーの指示）。**出荷するのは処理系であって、この例題ではない。**
利用者は自分の Lean パッケージでこのライブラリに依存し、業務ロジックと定理を書き、JS を生成する。
npm に出るのは利用者の成果物のほうで、`packages/verified-example` はその形の見本にとどまる。

## ゴール

このマイルストーンの終わりに立っている場所。

- 利用者が**自分のロジックについて定理を書ける**ことが、現実的な題材で確かめられている（完了）
- そのための語彙がライブラリ側にあり、評価器の内部を知らなくても書ける（完了）
- 式の形が凍っている。`Core.Expr` はこれ以降増えず、語彙は既存の形の腕として足す（完了）
- 型の健全性が証明され、証明が覆う式の形が 3 形から広がっている（完了）
- **他人の Lean パッケージからこの処理系を使える**（完了）

## 非目標

| 外すもの | 理由 |
| --- | --- |
| Promise / async | 保証の組み立てが作り直しになる。答えが引数だけで決まらなくなり、実行順序が観測可能になり、停止性が消え、検証が値の比較からやりとりの列の比較に変わり、生成 JS の模型にイベントループが要る。得られるのはユースケース層の薄い接着剤で、それは TS 側に置ける（決定 2026-09-07, ユーザーの指示） |
| クロージャ（ラムダを値にする） | 値にクロージャが入ると `encodeValue` が全域でなくなり、`Agree` の値比較・境界の型検査・`Correct` の環境の対応がすべて動く。コンビネータのその場のラムダで業務ロジックには足りている |
| 公開境界に関数を出すこと | 外から来た関数が純粋で決定的であることは検査できない。許せば「渡された関数が純粋であるかぎり」という但し書きが製品の保証に付く。Step 1 で消した但し書きを別の場所で買い戻すことになる（決定 2026-09-07, ユーザーの指示） |
| 比較関数を取る `sortBy` | 全順序であることと、等しいキーでの安定性が Lean 側と一致することの両方が要る。意味論に新しい概念を足す側。キーを取る `Arr.sortByKey` は全順序がキーの型から出るので、のちに入った（`docs/sort-plan.md`） |
| Float | `docs/business-logic-plan.md` の判断のまま |

## Approach

原則が三つあり、Step の順序はこの三つから出る。

**分子を優先する。** 表現力を足すほど、証明が覆う割合の分母が増える。今回の主軸は分子のほう。分母に
足してよいのは**既存の形を再利用するもの**だけで、意味論に新しい概念（クロージャ・非同期・全順序）は
1 つも足さない。

**言語を凍らせてから証明する。** 型の健全性は「式の形すべて」についての主張なので、後から形を足せば
その都度戻ることになる。だから構文の追加を先に終え、そのあとで証明に入る。順序が逆だと同じ証明を
二度書く。

**保証の但し書きを増やさない。** 関数引数は内部の宣言どうしに限る。関数型が公開境界に出ないので、
入口の実行時検査もベクタ生成も今のまま動き、条件つきの保証にならない。

## Step 1. 利用者定理の実地試験 — 完了

**確かめたこと**: 利用者が自分の業務ロジックについて定理を書けるか。現実的な性質を 3 本、実際に証明した。

- 下書き状態の注文は、何を渡しても出荷を拒否する（4 分岐の状態機械）
- 数量は何を渡しても 1 以上 999 以下に収まる（入れ子の条件式に対する全称）
- 同じ通貨どうしの、合計が Int53 に収まる加算は必ず成功する（構造体と `Result`）

manifest の定理は 1 本から 4 本になり、`Axioms.lean` の固定も 4 本に増えた。

**結果: 書けるが、素手では書けなかった。** 3 本とも、`add_comm` の書き方（評価器を丸ごと `simp` に
渡す）では通らない。詰まった場所は 2 つあり、どちらも例題ではなくライブラリ側の欠落だった。

**1. `Ty.subst` と `bindVars` が `partial` だった。** `partial` な定義は証明の中で一切展開できない。
この 2 つは宣言の型からフィールドの型を引くときに必ず通るので、**フィールドを持つ型を引数に取る関数に
ついては、どんな定理も 1 歩目から進めなかった**。`draft` のようにフィールドを持たないコンストラクタ
だけが偶然通っていた。構造的な再帰に書き直して解消（生成物は 1 バイトも動かない）。

**2. 評価器を 1 段ずつ開く語彙がなかった。** `evalExpr.eq_def` は右辺に `evalExpr` を含むので `simp` に
渡すと止まらず、fuel 10000 と出荷プログラム全体を相手に再帰深度が尽きる。必要だったのは、
公開関数の入口を 1 度で越える `evalCall_eq` と、構文の形ごとに 1 段だけ開く補題。使った 9 形分を
`Eval.lean` に置いた。

**したがって Step 2 が立つ。** 語彙は 9 形分しかなく、残りの形は同じ壁の手前にある。

## Step 2. 利用者向けの推論語彙 — 完了

**書けるようになったこと**: 利用者が自分のプログラムについて、評価器の内部を知らずに定理を書ける。

**置いたもの**:

- `Eval.lean` — 公開関数の入口を 1 度で越える `evalCall_eq`、`Core.Expr` の **35 形すべて**の 1 段展開
  （`&&` / `||` の短絡は一般の二項演算と別の形なので別立て）、そして `evalArgs` / `evalMapItems` /
  `evalFilterItems` / `evalReduceItems` の空・非空
- `Value.lean` — 入口の型検査を読むための補題。値と型の組み合わせごとに 1 本と、フィールド・要素・
  辞書の走査の空・非空

**`Ty.subst` と `bindVars` を構造的な再帰にした。** `partial` を外しただけでは整礎再帰になり、型定義の
探索が `rfl` で閉じない。リストの補助関数を通す形にすると構造的再帰として通り、利用者が自分の型に
ついて書く探索の補題（`Money.findAt? [] "Money" = ...`）が `rfl` の 1 行で済む。

**受け入れ条件は満たした。** Step 1 の 3 本を語彙だけで書き直すと、証明から処理系の内部
（`typeDef` / `TypeDef.ctorsAt` / `Ty.subst` / `bindVars` / `Value.hasTy` の直接展開）が消えた。
利用者が名前を出すのは、自分の宣言・自分の型の探索の補題・語彙の 3 種類だけになる。

## Step 3. 既存の形を再利用する構文追加 — 完了

**書けるようになったこと**: 業務ロジックでよく要るのに無かった操作。意味論に新しい概念は 1 つも
入っていない。

| 追加 | 置いた場所 |
| --- | --- |
| 文字列の `endsWith` | `StrBinOp` |
| `abs` | `UnOp` |
| `min` / `max` | `BinOp` |
| 配列の `++` | 既存の `BinOp.concat` を配列へ広げた |
| 辞書の `values` / `delete`、配列の `slice` / `reverse` | `Core.Expr` に 4 形 |
| 配列の `find` / `all` / `any` | `Core.Expr` に 2 形。`all` と `any` は走査が止まる条件が違うだけなので、`QuantOp` を持つ 1 形にまとめた |

**増えた形は 6 つ。** 演算子の enum に置けるものはそちらに置いた。形を足したものはすべて `Step` の
継続フレームと 1 段展開補題を同じコミットで持っている。

**短絡は `eval` と `Step` の両方に入っている。** `find` / `all` / `any` は答えが決まった時点で走査を
やめるので、後ろの要素で trap する述語はそこまで届かない。`reduce` への脱糖では同じことが言えない。

**範囲外は clamp せず trap する。** 配列の `slice` は、端が配列の外にある窓を短く詰めるのではなく
`indexOutOfBounds` で落ちる。添字の読みと `substring` がすでにそうしている。

**`runtime` の非空行は 204。** ここに入るものは検証されていない JS としてそのまま TCB に乗る。

**保証の境界**: 変わらない。

## Step 4. 内部限定の関数引数 — 完了

**書けるようになったこと**: 宣言済みの関数を名前で他の関数に渡せる。「割引ルールを差し替えられる集計
関数」が書ける。ラムダは値にならないまま。

**形**: 関数型（`(Int53) => Int53`）は引数の型にだけ書ける。渡せるのは `@name` で名指しした宣言だけで、
`Core.Expr` に増えたのはその参照を表す `fnRef` の 1 形。適用は既存の呼び出しがそのまま担う。

**公開かどうかは注釈ではなく引数の型で決まる。** 関数型の引数を持つ宣言は `export` されず、`.d.ts`
にも manifest の公開 API にも出ず、ベクタも作られない。それを呼ぶ公開関数を通して全件検査には乗る。

**関数型は 1 階に留まる。** 関数型の引数と結果に関数型は書けず、返り値・`let`・フィールド・`Array` /
`Option` / `Dict` / `Result` の中にも書けない。入口の実行時検査が覗く先に関数型が現れないので、検査も
ベクタ生成も今のまま動く。

**渡せるのは、受け取る宣言より前に宣言された関数だけ。** これがないと引数を経由した呼び出しが宣言順を
飛び越え、呼び出しグラフが循環しうる。この制限で「呼び出しは必ず前へ進む」が引数経由でも保たれ、
停止性の議論は今までのまま。

**保証の境界**: 変わらない。**但し書きは 1 つも増えていない。**

## Step 5. 型の健全性 — 完了

**証明したこと**: コンパイラが型 `T` と判断した式を `eval` が評価して値が返るなら、その値は `T` を
満たす（`Sound.lean` の `typeSound`）。

**なぜ要ったか**: 生成コードは被演算子の型で分岐する（`a + b` は `Int53` なら加算、`String` なら連結）。
証明の中では「コンパイラの見立て」と「環境の実際の値」が噛み合っていることを言えないので、算術の
場合分けが閉じなかった。

**形**: 環境が文脈と噛み合っていること（`EnvTyped`）を仮定して、fuel についての帰納法で示す。式の形を
足しても帰納法の構造は変わらないので、覆う形は `TypeChecked` に 1 つずつ足していける。いま覆っているのは
リテラル・変数・条件式・`let` 束縛・単項演算・二項演算の 6 形。

**`Ty` の `BEq` を手書きにした。** コンパイラは分岐の型が一致することを `==` で見るが、`Ty` は
`List Ty` を含む入れ子の帰納型なので `DecidableEq` も `LawfulBEq` も導出できず、「`==` が真なら等しい」
が言えなかった。`Value.beq` と同じ形の構造的な定義に書き換え、`Ty.eq_of_beq` を証明した。

**`call` が残っている理由**: 呼び出しの型は呼ばれる宣言の返り値型なので、覆うには宣言の本体が使いうる
**すべての形**を覆う必要がある。プログラム全体の整合性を帰納法に載せる作業で、形を 1 つ足すのとは
規模が違う。

**外から見て何も変わらない。** 生成物は 1 バイトも動いていない。

## Step 6. 証明の覆う範囲を広げる — 完了

**分子は 3 形から 6 形へ動き、二項演算は 16 演算子すべてが入った。** `fragment_correct` が覆うのは、
リテラル・変数・条件式に加えて `let` 束縛・単項演算（`!` / 単項マイナス / `abs`）・二項演算。演算子で
選り分けるものが無くなったので、覆う演算子を数えていた述語は消えた。

**算術は被演算子の型を 3 つとも覆っている。** `Int53` は `__i53` の範囲検査ごと、`UInt32` は
`>>> 0` と `Math.imul` の巻き戻しごと、`BigInt` はそのまま。`UInt32` の巻き戻しは
`(x + y) % 2^32` として JS の模型と突き合わせてある。ゼロ除算は両側とも trap する形で一致する。

**外から見て何が変わったか**: これらの形について言えることが「24431 件試して全部合っていた」から
「どんな入力でも合う」に変わった。**試していない入力についても言えることが、テストとの差。**

**`fragment_correct` に環境の仮定が付いた。** 型の健全性を使うので、環境が文脈と噛み合っていること
（`EnvTyped`）を仮定する。公開関数の入口はその型検査を通ってから本体に入るので、出荷している成果物では
この仮定は成り立っている。

**比較は順序を持つ 4 つの型すべてを覆っている。** `Int53` と `BigInt` は `eval` と模型が同じ
`compare` を使う。`UInt32` は `eval` が `Nat` を、模型が `Int` を比べるので、その間に 1 行の補題が挟まる。
`String` は生成コードが `__strcmp` を通し、その模型はコードポイント順、`eval` 側は Lean の
`Ord String`。**この 2 つが一致することは `rfl` では出ない** —— Lean の順序は `String.lt` を経由する
ので、両方を `List.compareLex` まで降ろして突き合わせている（`string_compare_toList`）。

**等値は型を付けて証明した。** スカラーは `===`（模型の `sameValue`）、それ以外は `__eq` の深い等値。
**「符号化しても等値が保たれる」は型を付けないと成り立たない** —— `Int53 0` と `UInt32 0` はどちらも
JS 側で `.num 0` になるので、`Value.beq` では偽、`JsValue.beq` では真になる。だから補題は「同じ型を
満たす 2 つの値について」の形で、値の構造と型を両方持って回る帰納法になっている
（`beq_encodeValue`）。

**どこで止めたか**: 残るのは `call` と、パターンマッチ・配列の走査・辞書。`call` は Step 5 に書いた
とおり、覆うには宣言の本体が使いうるすべての形を覆う必要があり、形を 1 つ足すのとは規模が違う。その先へ
行くほど証明は重くなる一方、全件検査で見えている安心感との差は縮む。35 形すべては目指さない。

**保証の境界**: 動いた。README の「保証の組み立て」と `docs/mvp-plan.md` の Phase 2 到達点は同じ
コミットで直してある。

## Step 7. 他人の Lean パッケージから使えるようにする — 完了

**できるようになったこと**: 利用者が自分の Lean パッケージを作り、このライブラリに依存し、自分の業務
ロジックと定理を書き、自分の npm パッケージを生成できる。

**`emit` がライブラリに入った。** `Main.lean` に焼き込まれていた書き出し手順は `Lean2Js/Emit.lean` へ
移り、`Manifest` を受け取るだけになった。`Main.lean` は渡されたモジュールの `manifest` を実行時に
読む汎用ドライバで、利用者はこれを `lake exe lean2js` で呼ぶ。

**ライブラリのルートから例題が外れた。** `Lean2Js.lean` が持つのは処理系だけで、`Example` /
`Tests` / `Axioms` はこのリポジトリの実行ファイルが読む。`import Lean2Js` で例題は付いてこない。

**雛形は `templates/verified-package/`。** `lakefile.toml`（git 経由の `Lean2Js` 依存）、最小の
プログラム、定理 1 本とその `Claim`、書き換えどころを書いた README。
`scripts/check-template.sh` が雛形を空のディレクトリに展開し、依存を作業ツリーへ向け替えて
`lake build` と `lake exe lean2js` を通し、npm パッケージが出ることを CI で確かめている。

**Reservoir への登録は残っている。** git の `rev` を指した `require` で今日から使えるので、雛形も
CI もそれで動く。Reservoir に載せるのは公開の作業なので、このリポジトリの持ち主が決めること。

## 順序と依存

```
Step 1（実地試験・完了）
  ↓ 結果として Step 2 が立った
Step 2（語彙・完了）
  ↓
Step 3（構文追加・完了） → Step 4（関数引数・完了）   式の形はここで凍った
  ↓
Step 5（型の健全性・完了） → Step 6（証明の拡張・完了）   凍った言語に対して証明する

Step 7（配布・完了）   どれとも独立
```

**Step 5 は Step 3 / 4 より後**（形を足すたびに帰納法へ戻るため）、**Step 6 は Step 5 より後**
（型の健全性がないと算術の場合分けが閉じないため）。Step 7 はどれとも独立なので、先に済ませた。

**`Core.Expr` に形を足したら、その形の 1 段展開補題も同じコミットで足す。** 語彙は形ごとに 1 本なので、
足し忘れるとその形を使う宣言だけ証明できない状態になる。

## 守ること

- **保証を弱めて緑にしない。** 実行時検査が落ちたときに、検査対象のベクタを減らさない
- **`sorry` で塞がない。** 塞げば `Axioms.lean` が落ちる
- **manifest に定理を足したら `Axioms.lean` に行を足す**
- **数字を動かしたら引用元を同じコミットで直す。** ベクタ件数・`exports` 件数・`runtime` の非空行数・
  証明が覆う形の数は、README と `docs/mvp-plan.md` が引用している
- **保証の境界を動かしたら**、README の「保証の組み立て」と `docs/mvp-plan.md` の到達点を同じコミットで
  直す
- **プッシュ前にゲートを全部ローカルで通す。** 一部だけ回した結果を判断に使わない
