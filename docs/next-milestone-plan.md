# 次のマイルストーン計画

`docs/business-logic-plan.md` が業務ロジックを書ける幅まで広げたあと、**保証の厚みと配布**へ主軸を移す
ための計画。

## 文脈

到達している地点は、出荷している成果物の数字で言える。公開関数 51 本、型 5 つ、出荷前に照合する
差分ベクタ 18665 件。証明が覆っているのは `Core.Expr` の 28 形のうち 3 形（リテラル・変数・条件式）で、
残りは `Agree` の全件検査が受けている。manifest に載っている定理は 4 本。

配布の形は決まった（決定 2026-09-07, ユーザーの指示）。**出荷するのは処理系であって、この例題ではない。**
利用者は自分の Lean パッケージでこのライブラリに依存し、業務ロジックと定理を書き、JS を生成する。
npm に出るのは利用者の成果物のほうで、`packages/verified-example` はその形の見本にとどまる。

## ゴール

このマイルストーンの終わりに立っている場所。

- 利用者が**自分のロジックについて定理を書ける**ことが、現実的な題材で確かめられている（完了）
- そのための語彙がライブラリ側にあり、評価器の内部を知らなくても書ける（完了）
- 言語が凍っている。これ以降、意味論に概念を足さない
- 型の健全性が証明され、証明が覆う式の形が 3 形から広がっている
- **他人の Lean パッケージからこの処理系を使える**

## 非目標

| 外すもの | 理由 |
| --- | --- |
| Promise / async | 保証の組み立てが作り直しになる。答えが引数だけで決まらなくなり、実行順序が観測可能になり、停止性が消え、検証が値の比較からやりとりの列の比較に変わり、生成 JS の模型にイベントループが要る。得られるのはユースケース層の薄い接着剤で、それは TS 側に置ける（決定 2026-09-07, ユーザーの指示） |
| クロージャ（ラムダを値にする） | 値にクロージャが入ると `encodeValue` が全域でなくなり、`Agree` の値比較・境界の型検査・`Correct` の環境の対応がすべて動く。コンビネータのその場のラムダで業務ロジックには足りている |
| 公開境界に関数を出すこと | 外から来た関数が純粋で決定的であることは検査できない。許せば「渡された関数が純粋であるかぎり」という但し書きが製品の保証に付く。Step 1 で消した但し書きを別の場所で買い戻すことになる（決定 2026-09-07, ユーザーの指示） |
| `sortBy` | 比較関数が全順序であることと、等しいキーでの安定性が Lean 側と一致することの両方が要る。意味論に新しい概念を足す側 |
| Float | `docs/business-logic-plan.md` の判断のまま |

## Approach

原則が三つあり、Step の順序はこの三つから出る。

**分子を優先する。** 表現力を足すほど、証明が覆う割合の分母が増える。今回の主軸は分子のほう。分母に
足してよいのは**既存の形を再利用するもの**だけで、意味論に新しい概念（クロージャ・非同期・全順序）は
1 つも足さない。

**言語を凍らせてから証明する。** 型の健全性は「式の形すべて」についての主張なので、後から形を足せば
その都度戻ることになる。だから構文の追加を先に終え、そのあとで証明に入る。順序が逆だと同じ証明を
二度書く。

**保証の但し書きを増やさない。** 関数引数は内部の宣言どうしに限る。関数型が公開境界に出ないので、
入口の実行時検査もベクタ生成も今のまま動き、条件つきの保証にならない。

## Step 1. 利用者定理の実地試験 — 完了

**確かめたこと**: 利用者が自分の業務ロジックについて定理を書けるか。現実的な性質を 3 本、実際に証明した。

- 下書き状態の注文は、何を渡しても出荷を拒否する（4 分岐の状態機械）
- 数量は何を渡しても 1 以上 999 以下に収まる（入れ子の条件式に対する全称）
- 同じ通貨どうしの、合計が Int53 に収まる加算は必ず成功する（構造体と `Result`）

manifest の定理は 1 本から 4 本になり、`Axioms.lean` の固定も 4 本に増えた。

**結果: 書けるが、素手では書けなかった。** 3 本とも、`add_comm` の書き方（評価器を丸ごと `simp` に
渡す）では通らない。詰まった場所は 2 つあり、どちらも例題ではなくライブラリ側の欠落だった。

**1. `Ty.subst` と `bindVars` が `partial` だった。** `partial` な定義は証明の中で一切展開できない。
この 2 つは宣言の型からフィールドの型を引くときに必ず通るので、**フィールドを持つ型を引数に取る関数に
ついては、どんな定理も 1 歩目から進めなかった**。`draft` のようにフィールドを持たないコンストラクタ
だけが偶然通っていた。構造的な再帰に書き直して解消（生成物は 1 バイトも動かない）。

**2. 評価器を 1 段ずつ開く語彙がなかった。** `evalExpr.eq_def` は右辺に `evalExpr` を含むので `simp` に
渡すと止まらず、fuel 10000 と 51 宣言のプログラムを相手に再帰深度が尽きる。必要だったのは、
公開関数の入口を 1 度で越える `evalCall_eq` と、構文の形ごとに 1 段だけ開く補題。使った 9 形分を
`Eval.lean` に置いた。

**したがって Step 2 が立つ。** 語彙は 9 形分しかなく、残り 19 形は同じ壁の手前にある。

## Step 2. 利用者向けの推論語彙 — 完了

**書けるようになったこと**: 利用者が自分のプログラムについて、評価器の内部を知らずに定理を書ける。

**置いたもの**:

- `Eval.lean` — 公開関数の入口を 1 度で越える `evalCall_eq`、`Core.Expr` の **28 形すべて**の 1 段展開
  （`&&` / `||` の短絡は一般の二項演算と別の形なので別立て）、そして `evalArgs` / `evalMapItems` /
  `evalFilterItems` / `evalReduceItems` の空・非空
- `Value.lean` — 入口の型検査を読むための補題。値と型の組み合わせごとに 1 本と、フィールド・要素・
  辞書の走査の空・非空

**`Ty.subst` と `bindVars` を構造的な再帰にした。** `partial` を外しただけでは整礎再帰になり、型定義の
探索が `rfl` で閉じない。リストの補助関数を通す形にすると構造的再帰として通り、利用者が自分の型に
ついて書く探索の補題（`Money.findAt? [] "Money" = ...`）が `rfl` の 1 行で済む。

**受け入れ条件は満たした。** Step 1 の 3 本を語彙だけで書き直すと、証明から処理系の内部
（`typeDef` / `TypeDef.ctorsAt` / `Ty.subst` / `bindVars` / `Value.hasTy` の直接展開）が消えた。
利用者が名前を出すのは、自分の宣言・自分の型の探索の補題・語彙の 3 種類だけになる。

## Step 3. 既存の形を再利用する構文追加

**書けるようになること**: 業務ロジックでよく要るのに今ない操作。**新しい概念を持ち込まないものだけ**を
採る。

| 追加 | 再利用する形 |
| --- | --- |
| 配列の `find` / `all` / `any` | `map` / `filter` と同じ束縛つきの形。短絡が要るので `reduce` への脱糖では代用できない（述語が trap しうる） |
| 配列の `slice` / `concat` / `reverse` | 束縛なし。範囲外の扱いは既存の添字と同じく trap |
| 辞書の `values` / `delete` | `get` / `set` と同じ形 |
| 文字列の `endsWith` | `startsWith` と同じ形。UTF-16 単位で見た答えとコードポイントで見た答えが一致する側 |
| `abs` / `min` / `max` | 既存の算術と同じ trap 規則 |

**触る場所**: `Core` / `Eval` / `Compile` / `JsSem` / `Step` / `Js.runtime`、そして `Example.lean`。
束縛を持つ 3 つは `Step` に継続フレームが要る。

**`runtime` の増分を数える。** ここに入るものは検証されていない JS としてそのまま TCB に乗る。
現在の非空行は 172。

**ベクタは自動では増えない。** 公開関数ごとに作られるので、追加した操作を使う宣言を `Example.lean` に
足して初めて検査される。

**保証の境界**: 変わらない。**動かすドキュメント**: README のサブセット表、ベクタ件数、`exports` 件数。

## Step 4. 内部限定の関数引数

**書けるようになること**: 宣言済みの関数を名前で他の関数に渡す。「割引ルールを差し替えられる集計関数」
のような書き方。ラムダは値にならないまま。

**形**: 関数型を持つ引数は**名前でしか渡せない**。渡せるのはこの処理系が生成した宣言だけなので、
`eval` はプログラムから引いて実行でき、外部関数を表としてモデル化する仕組みが要らない。

**関数型を引数に持つ宣言は公開されない。** 公開関数の署名（入れ子も含む）に関数型が現れることを
コンパイラが拒否する。これで境界の実行時検査もベクタ生成も無傷のまま、`.d.ts` に関数型が出ない。
内部の宣言は、それを呼ぶ公開関数を通して全件検査に乗る。

**保証の境界**: 変わらない。**但し書きが増えないことがこの Step の設計そのもの。**

**動かすドキュメント**: README のサブセット表（「関数を値にしない」制約の記述）、`exports` 件数。

## Step 5. 型の健全性

**証明すること**: コンパイラが型 `T` と判断した式を `eval` が評価して値が返るなら、その値は `T` を
満たす。

**なぜ要るか**: 生成コードは被演算子の型で分岐する（`a + b` は `Int53` なら加算、`String` なら連結）。
証明の中では「コンパイラの見立て」と「環境の実際の値」が噛み合っていることを言えないので、算術の
場合分けが閉じない。`docs/mvp-plan.md` と `docs/business-logic-plan.md` の両方が、これを次の
ブロッカーとして名指ししている。

**外から見て何も変わらない。** 生成物は 1 バイトも動かず、買い手に見えるものも増えない。Step 6 の
土台。

**Step 3 / 4 の後に置く理由**: 式の形すべてについての帰納法なので、形を足すたびに戻ることになる。

**保証の境界**: 変わらない（単独では）。

## Step 6. 証明の覆う範囲を広げる

**証明すること**: `InFragment` を算術・単項演算・`let` 束縛・関数呼び出しへ広げる。**3/28 の分子が
動くのはここ。**

**外から見て何が変わるか**: これらの形について言えることが「18665 件試して全部合っていた」から
「どんな入力でも合う」に変わる。**試していない入力についても言えることが、テストとの差。**

**どこで止めるか**: パターンマッチ・配列の走査・辞書まで行くと証明が重くなる一方、全件検査で見えている
安心感との差は縮む。28 形すべては目指さない。**このマイルストーンの終わりに、どの形が証明済みでどの形が
全件検査かを README に列挙できる状態にする。**

**保証の境界**: 動く。**動かすドキュメント**: README の「保証の組み立て」と `docs/mvp-plan.md` の
Phase 2 到達点を同じコミットで。

## Step 7. 他人の Lean パッケージから使えるようにする

**できるようになること**: 利用者が自分の Lean パッケージを作り、このライブラリに依存し、自分の業務
ロジックと定理を書き、自分の npm パッケージを生成する。

**今そうなっていない理由**: `leants` は出力先を受け取るだけで、書き出す中身は `Example.manifest` が
焼き込まれている。他人のプログラムを渡す口がない。**いまの実行ファイルは処理系ではなく、このリポジトリの
例題を書き出すビルド手順。**

**形**: 定理は証明項であってデータではないので、ファイルを 1 つ読み込む形の CLI では運べない。利用者は
Lean のパッケージを書き、自分の manifest を `emit` に渡す小さな実行ファイルを持つ。**したがって
成果物は「配布する CLI」ではなく「利用者側のパッケージの雛形」になる。**

- ライブラリを Reservoir から引ける形に整える
- 雛形（`lakefile` / 最小のプログラム / 定理 1 本 / 生成を回す実行ファイル）を用意する
- 雛形を空のディレクトリから通して、npm パッケージが出ることを確かめる

**動かすドキュメント**: README のロードマップ（Phase 3 の「package publishing」は npm への公開では
なく処理系の配布を指す）、`docs/mvp-plan.md` の Phase 3、README の「開発」節に利用者側の導線。

## 順序と依存

```
Step 1（実地試験・完了）
  ↓ 結果として Step 2 が立った
Step 2（語彙・完了）
  ↓
Step 3 → Step 4   言語を広げ、ここで凍らせる
  ↓
Step 5 → Step 6   凍った言語に対して証明する
```

Step 7 はどれとも独立で、いつ差し込んでもよい。**Step 5 は Step 3 / 4 より後**（形を足すたびに帰納法へ
戻るため）、**Step 6 は Step 5 より後**（型の健全性がないと算術の場合分けが閉じないため）。

**Step 3 で形を足したら、その形の 1 段展開補題も同じコミットで足す。** 語彙は形ごとに 1 本なので、
足し忘れるとその形を使う宣言だけ証明できない状態になる。

## 守ること

- **保証を弱めて緑にしない。** 実行時検査が落ちたときに、検査対象のベクタを減らさない
- **`sorry` で塞がない。** 塞げば `Axioms.lean` が落ちる
- **manifest に定理を足したら `Axioms.lean` に行を足す**
- **数字を動かしたら引用元を同じコミットで直す。** ベクタ件数・`exports` 件数・`runtime` の非空行数・
  証明が覆う形の数は、README と `docs/mvp-plan.md` が引用している
- **保証の境界を動かしたら**、README の「保証の組み立て」と `docs/mvp-plan.md` の到達点を同じコミットで
  直す
- **プッシュ前にゲートを全部ローカルで通す。** 一部だけ回した結果を判断に使わない
