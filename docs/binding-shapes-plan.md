# 束縛を変えて評価する形

`docs/value-shapes-plan.md` が断片を「部分式を評価して値を組み立てるだけの形」まで広げたあと、
残っていたのは**評価する環境が実行時に決まる形**だった。このマイルストーンはそのうち `match` と
配列走査 5 形を断片へ入れ、`call` / `fnRef` だけを外に残した。

## 文脈

断片は `Core.Expr` の 35 形のうち 27 形、公開関数 67 本のうち 43 本に届いていた。外れていた 24 本を
外れる理由で数えると、こうなっていた。

| 外れる理由 | 本数 |
| --- | --- |
| `match` だけ | 8 |
| 走査（`map` / `filter` / `find` / `all` / `any` / `reduce`）だけ | 7 |
| `call` / `fnRef` だけ | 4 |
| `match` または走査に加えて `call` | 5 |

`match` と走査を入れれば 58 本になり、残る 9 本はすべて `call` を通る。だから `call` はこの
マイルストーンの外に置いた —— 呼び出しを覆うには宣言の本体が使いうるすべての形をプログラム全体の
整合性ごと帰納法に載せる必要があり、`Sound.lean` が `call` を外しているのと同じ理由による。

## Approach

**形の族ごとに刻み、Sound を先に置いた。** `TypeChecked` も `InFragment` も帰納型で、`typeSound` /
`fragment_correct_in` / `fragment_traps_in` はその上の 1 本の帰納だから、構成子を足したコミットは
その場合分けも同じコミットで埋めないと通らない。生成コードが値の形で分岐する以上（`.map` は `.arr`
にしか効かず、腕のテストは `.obj` の `tag` を読む）、先に要るのは `Sound` のほうだった。

**走査を先に、`match` を後に。** 走査は `eval` と JS の模型が**同じ形の補助関数**として書いてある
（`evalMapItems` と `evalMapJs`、`evalReduceItems` と `evalReduceJs`）。要ったのは fuel の帰納の内側に
置くリストの帰納だけで、帰納法の仮定が環境と fuel について全称なので、要素ごとに違う環境へそのまま
効いた。`match` はそうではない —— 生成コードはパターンをテストと束縛に落とした条件の連鎖で、
`matchPat` との対応はパターンについての別の帰納になる。

**陽性と陰性は同じコミット。** `InFragment` に構成子を 1 つ足すと `fragment_correct_in` と
`fragment_traps_in` の両方に穴が開く。片方だけ埋めることはできない。

## 何が動いたか

### 走査 5 形

`TypeChecked` / `InFragment` に 5 形、`Sound` と `Correct` に走査ごとの補題を置いた。
`filter` / `find` / `all` / `any` の型の健全性は帰納法の仮定を要らない —— 返るのは渡された要素か、
決めた `Bool` だから。要るのは `map` と `reduce` で、`reduce` は累算器の型を不変条件として運ぶ。

**短絡はそのまま写る。** `find` / `all` / `any` は答えが決まった時点で走査をやめ、模型も同じ形で
やめる。補題は「走査の途中で止まった結果」をそのまま持つ。

### `match`

腕の連鎖を歩く補題（`eventually_chain` / `eventuallyErr_chain`）が中心で、その下に

- `patParts_matched` — 一致した腕はテストがすべて `true` に評価され、`paths` から読んだ値が
  `matchPat` の束縛と一致する
- `patParts_unmatched` — 一致しなかった腕は、決め手のテストが `false` に評価され、その前のテストは
  `true`。**後ろのテストについては何も言わない** —— `&&` が短絡するので、タグが違う値のフィールドを
  読むテストはそもそも評価されない

がある。この 2 本はパターンについての相互帰納で、リスト版と合わせて 4 本。

### 名前の捕獲を閉じた

`match` は生成コードで scrutinee を `__s` に束縛する。リファレンス環境が同じ名前を束縛していたら、
生成コード側は scrutinee を、`eval` 側は利用者の値を読む —— **一致は成り立たない**。

`JsEnvAgrees` を構造体にして `scrutFree`（リファレンス環境は `scrutName` を束縛しない）を持たせた。
`JsEnvAgrees.cons` は「足す名前が `__s` でないこと」を要求し、それは `validateIdent` が `__` 接頭辞を
拒むことから出る。入口の環境については `Unreserved` が同じことを言っていて、`decl_correct` がそこで
discharge する。**利用者から見える主張に但し書きは増えていない。**

### 網羅性検査は写せない

`fragment_traps_in` が運べる失敗を `Correct.Mirrorable` として名前を付けた。除くのは 2 つ。

- `outOfFuel` — 従来どおり。fuel は `eval` を全域にするための装置で、生成コード側の主張は
  「十分な燃料で」の形をしている
- `noMatchingAlternative` — **今回増えた**。網羅性はコンパイル時に検査済みなので、生成した連鎖は
  最後の腕をテストなしで取る。`eval` の拒否を写すには網羅性検査そのものの正しさが要り、その検査
  （`useful`）は `partial` —— 証明の中で展開できない

**これは保証の境界が動いたということ。** README の「保証の組み立て」と `docs/mvp-plan.md` の到達点は
同じコミットで直してある。`useful` を構造的な再帰に書き直して網羅性を証明すれば、この除外は消える。

### 検査器がプログラム全体を読むのをやめた

`signature` / `useful` / `firstUnreachable` / `patParts` は `Program` ではなく `List TypeDef` を取る。
宣言は自分より前の宣言だけを見てコンパイルされるので、`compileExpr_types_irrel`（型が同じなら
コンパイル結果も同じ）が `match` について必要になる。`useful` は `partial` で、`useful p ...` と
`useful q ...` を関係づける方法が無い。**型宣言だけを渡せば同じ項になる。**

### 数字

| | 前 | 後 |
| --- | --- | --- |
| 断片が覆う `Core.Expr` の形 | 27 / 35 | 33 / 35 |
| 陽性・陰性が届く公開関数 | 43 / 67 | 58 / 67 |
| manifest の `Claim` | 9 | 12 |

生成した JS は 1 バイトも動いていない。動いたのは manifest に増えた 3 本の定理だけで、ベクタも
24431 件のまま。

## 覆っていないもの

| 外れるもの | 理由 |
| --- | --- |
| `call` / `fnRef` と、それを使う公開関数 9 本 | 覆うにはプログラム全体の整合性を帰納法に載せる必要がある。`Agree` の全件検査が受け持つ |
| `outOfFuel` | 参照側だけの概念で、JS 側に写す相手がいない |
| `noMatchingAlternative` | 上のとおり。網羅性検査の正しさが先に要る |
| `tag` という名前のフィールドの射影 | 判別子のキーと衝突する。`validateType` が型の宣言時に拒否している |

## 守ること

- **保証を弱めて緑にしない。** 実行時検査が落ちたときに、検査対象のベクタを減らさない
- **`sorry` で塞がない**（塞げば `Axioms.lean` が落ちる）
- **manifest に定理を足したら `Axioms.lean` に行を足す**
- **数字を動かしたら引用元を同じコミットで直す。** 断片が覆う形の数と関数の本数は `README.md` と
  `docs/mvp-plan.md` が引用している
- **プッシュ前にゲートを全部ローカルで通す。** 一部だけ回した結果を判断に使わない
