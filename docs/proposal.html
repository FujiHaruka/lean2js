Proof-carrying
npm packages.

Leanで証明した業務ロジックを、React・Next.js・Node.jsから普通に使えるnpmパッケージとして配布する。

形式検証の導入に、フロントエンドの技術スタック交換は要らない。追加するのは、ひとつのパッケージだけ。
01 / PROBLEM

AIがコードを書くほど、テストだけでは追いつかない。

生成速度は上がっても、レビュー能力と保証の強さは比例しない。一方、従来の形式手法は本番のWeb開発から遠い。

VOLUME

実装量がレビュー能力を超える

AIは大量のコードを生成できるが、人間による逐次レビューはボトルネックになる。

CONFIDENCE

テストは反例の不在を証明しない

property testを含め、有限回の実行では「すべての入力」に対する保証にはならない。

ADOPTION

形式手法は既存スタックから遠い

専用言語や専用フレームワークへの全面移行は、導入コストが高すぎる。

02 / SOLUTION

証明した関数そのものを、本番で動かす。

JSと意味論が正確に対応するLeanサブセットを定義し、小さな検証済みコンパイラでESMへ変換する。

勝負する軸は「LeanからJSが出るか」ではない。既存のnpm・TypeScript開発へ、どれだけ自然に組み込めるか。

04 / DESIGN

制限は、弱点ではなく信頼性の設計。

Lean全体を対象にせず、JSとの対応が明快な領域に絞ることで、コンパイラの正しさと小さなTCBを現実的に狙う。

01

JSの意味論に合わせる

Int53、UInt32、BigIntなど、数値表現を曖昧にしない。

02

境界を型で固定する

公開APIはJS互換の値に限定し、ESMと.d.tsを同時生成する。

03

生成器より検査器を信頼する

将来はtranslation validationにより、生成結果の証明書を小さなcheckerで検査する。

04

証明を成果物に残す

定理・ビルド・コンパイラ版をproof manifestとして追跡可能にする。

初期サブセットに含める

05 / MVP

最初は「業務ロジックの小さな核」に絞る。

価格計算、権限判定、状態遷移、バリデーション。副作用の少ない重要ロジックから価値を証明する。

PHASE 1 / COMPILE

最小言語とESM出力

明確な意味論を持つサブセットを定義。

  • 基本型・ADT・純粋関数
  • index.js / index.d.ts
  • Nodeでの差分テスト
PHASE 2 / VERIFY

変換の保証

Lean評価とJS評価の一致を機械的に確認。

  • small-step semantics
  • compiler correctness
  • proof manifest
PHASE 3 / SHIP

npm開発体験

既存プロジェクトへ自然に導入可能にする。

  • source maps
  • tree shaking
  • CI / package publishing
CORE BET

Web開発者にLeanを売らない。
保証されたnpmパッケージを売る。

競合は他の定理証明支援系ではなく、AIが生成したTypeScriptとテストスイート。価値は、テスト件数の追加ではなく、出荷する実装へのmachine-checkableな保証にある。
